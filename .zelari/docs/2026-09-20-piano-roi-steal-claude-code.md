### WS1 — Policy engine permessi + `/permissions` (rec #3 del documento)

- **Obiettivo**: un solo motore `allow / ask / deny` valutato PRIMA del dispatch di ogni tool, con regole su tool+categoria+path (+host per network), override per sessione, transcript delle denials.
- **Perché #1**: i pezzi esistono già (categorie in `toolPermissions`, folder trust, jail, session grants) — manca solo il collante. È la frizione quotidiana più alta a costo più basso.
- **Scope**: nuovo `src/cli/safety/policyEngine.ts` (puro, ≤300 LOC, zod per le regole); nuovo slash handler `/permissions`; integrazione nel punto di dispatch dei tool CLI; evento denial strutturato sulla spine.
- **Out of scope**: classifier cloud, auto-approve ML, modifiche al jail win32. Il policy engine CONSUMA folder trust come input, non lo rimpiazza.
- **Acceptance** (verificabili, stile ADR-0023):
  1. Una regola `deny` su tool+path impedisce la chiamata e produce un evento strutturato nella spine, verificabile su replay.
  2. `/permissions` elenca le regole attive con sorgente (default / progetto / sessione) e permette add/remove a caldo.
  3. Le 5 categorie esistenti restano la semantica di default: zero regressioni nei test di safety esistenti.
  4. `npm run typecheck` e `npm run test` verdi.
- **Rischi**: collisione semantica con folder trust → mitigata dalla gerarchia esplicita (deny > ask > allow; folder trust = input). Taglia: **M**.
