# M2.3 — Audit determinismo del trailing context

Data: 2026-09-19 · Slice: **M2.3** (piano "cache hit rate" — `.zelari/docs/2026-09-18-cache-hit-rate-piano-implementazione.md`, sezione M2.3)
Stato: **consegnato** · Riferimenti: t131 (`.zelari/plan-tasks/t131.md`), M2.1 (t129), M2.2 (t130)

## Obiettivo

A parità di stato, il render del segmento volatile (che dopo M2.1 viaggia come messaggio
effimero `<context-update>` **dopo** la history) deve essere **byte-identico**. Un byte di
drift costa un miss anche sull'ultimo blocco, annullando il vantaggio dello spostamento.

## Metodo

1. Grep sui composer del volatile: `Date.now()|new Date(|randomUUID|Math.random|toISOString` in
   `src/cli/workspace/**` (workspace summary, compose context, plan summary, durable/RAG) e nel
   path del builder (`packages/core/src/agents/systemPromptBuilder.ts`).
2. Classificazione per campo: **frequenza di churn intra-sessione** e **visibilità utente**
   (regola del piano: quantizzare solo se la semantica utente non cambia).
3. Fix in-scope: memo del render + test di determinismo con allowlist esplicita.

Il builder puro è **già deterministico** (`buildSystemPromptSplit`: nessun `Date.now` / random /
ordinamento non stabile; i moduli sono ordinati per `priority` e i tool per nome), verificato in
`tests/unit/core-systemPromptSplit.test.ts` → describe `trailing context determinism (M2.3)`.

## Verifica (comandi eseguibili)

```bash
# 1. Nessun timestamp non quantizzato nel volatile (allowlist esplicita).
npx vitest run tests/unit/core-systemPromptSplit.test.ts   # describe "trailing context determinism (M2.3)"

# 2. Grep di audit sui composer (atteso: nessun hit nei composer del volatile).
#    src/cli/workspace/composeContext.ts → 0 hit
#    src/cli/workspace/workspaceSummary.ts → 0 hit
#    src/cli/workspace/planStore.ts → solo frontmatter (updatedAt/createdAt/completedAt), mai renderizzato nel prompt
```

## Deviazioni dal piano

- Il piano proponeva la quantizzazione (`timestamp → minuto`) come prima azione: l'audit mostra che
  **nessun timestamp raggiunge il volatile**, quindi non è stata applicata alcuna quantizzazione
  (sarebbe stata una modifica senza effetto). La regola "quantizza solo se la semantica utente non
  cambia" resta rispettata: i campi che churnano davvero (albero dei file, RAG, tail risorse) sono
  stato utente osservabile e restano churn accettato, ora **confinato nella coda della request**.
- La memoizzazione richiesta dal piano è implementata sul render (`wrapTrailingContext`): a parità di
  input la stringa restituita è quella precedente, byte per byte. Il fingerprint per-turno è coperto
  dai test di determinismo (input identici ⇒ output identico).
