# Zelari 2.6 — Piano di chiusura completa

**Baseline:** Zelari 2.6.0

**Target:** 2.6.1 per hardening/correttezza; 2.6.2 per il repair del budget per turno; 2.7 per rollout completo delle garanzie

**Obiettivo:** trasformare le capability già presenti in garanzie end-to-end, senza aggiungere nuove feature speculative.

**Stato verificato 2026-08-23:** Exit Gate 2.6.1 chiuso; il repair della semantica per-turno è verificato per la 2.6.2 (typecheck, 3134/3134 test e suite eval verdi). I residuali di wiring Mission e CI candidate-vs-baseline blocking restano esplicitamente nella 2.7 (`t12`, `t15`).

> **Principio:** core capability ≠ product guarantee. Il lavoro residuo è chiudere il lifecycle: `define → persist → resume → project → enforce → verify → evaluate → block regressions`.

---

## 1. Definition of Done

La 2.6 è realmente chiusa quando:

- ogni sessione registra un Harness Manifest completo;
- il manifest cambia quando cambia qualunque input comportamentale model-visible;
- ResourceBudget è l’unica autorità per i limiti tool;
- TUI e headless ricostruiscono lo stesso ResourceLedger;
- `maxToolCalls` ha una semantica univoca;
- verification reserve protegge davvero verify/repair mirati;
- il model context contiene un solo Resource Status;
- `resourceReserveGate` è nel completion lifecycle;
- TaskContract non produce falsi criteria;
- user steer aggiorna TaskContract in modo versionato;
- Kraken, Gauntlet, Mission e Verification condividono lo stesso TaskContract;
- budget continuation è realmente cablato;
- Gauntlet con budget zero va in `hold`;
- structural changes non riducono mai la copertura eval;
- un anchor baseline mancante nel candidate è regressione;
- AnchorRunner conserva manifest hash, policy hash e token usage reali;
- `maxTokens` è realmente enforceable;
- `runGate` confronta baseline/candidate e validity reali;
- CI è blocking almeno su Tier 0;
- esistono 15–25 historical anchors stabili;
- Unified Cost usa dati completi.

# 3. TaskContract — fix parser

La regex permissiva attuale non deve trattare ogni linea come acceptance criterion.

Accettare come criteria solo pattern espliciti:

```text
- [ ] ...
- [x] ...
Acceptance: ...
Criterion: ...
Verify: ...
Test: ...
Success: ...
```

Se non esistono criteria espliciti:

```ts
acceptanceCriteria = []
```

Le frasi normative devono diventare constraint, non automaticamente criteria.

Esempio:

```text
Fix login.
Do not change password semantics.
Keep Node 24 compatibility.
```

Atteso:

```text
goal:
Fix login.

constraints:
- Do not change password semantics.
- Keep Node 24 compatibility.

criteria:
[]
```

### Exit criteria

- zero false criteria nei fixture test;
- TaskContract può essere default-on senza proliferazione.

# 4. TaskContract — steer lifecycle

Aggiungere un updater host-neutral:

```ts
interface TaskContractUpdateInput {
  current: TaskContract;
  userMessage: string;
  userSeq: number;
}
```

Gli steer rilevanti producono:

```text
task.contract_updated
```

con version monotona e provenance.

Regole:

- user constraints non rimovibili da update agent-derived;
- user criteria required non eliminabili;
- goal rewrite solo da steer utente esplicito;
- append-only, mai mutation in-place.

`CompactionStateSnapshot` usa sempre la latest TaskContract version.

# 8. ResourcePolicy come unica autorità

```text

```


# 9. `maxToolCalls`: hard vs soft

Decisione consigliata:

```text
maxToolCalls = hard limit
softToolTarget = eventuale advisory target
```

Regola:

```text
used >= maxToolCalls
→ deny ogni nuova billable tool call
```

Non clampare `used`; conservare l’overrun reale:

```text
used = 42
limit = 40
remaining = 0
overrun = 2
```

Eventi:

```text
resource.limit_reached
resource.overrun
```

# 13. Verification Reserve argument-aware

La seam deve diventare:

```ts
toolCallGate(
  toolName: string,
  args: unknown,
  context: ToolGateContext

```

Usare:

```ts
isVerificationEssential(toolName, args, stage)
```

### Essential tipici



# 14. Wire `resourceReserveGate`

Lifecycle:

```text
VerificationEngine
      ↓
CompletionPolicy
      ↓
ResourceReserveGate
      ↓
final completion
```

Regole:

- deterministic PASS resta PASS;
- FAIL resta repair-required;
- non-PASS + budget esaurito → BLOCKED/resource-exhausted;
- il budget non può mai creare PASS.

Integrare in Kraken TUI/headless, Mission e finalizzazione Gauntlet.

# 17. Harness Change Classification

Non usare una gerarchia che fa prevalere `behavioral` su `structural`.

Preferire:

```ts
interface HarnessChangeSet {
  structural: string[];
  behavioral: string[];
  cosmetic: string[];
}
```

Policy:

```text
structural exists
→ full structural gate

behavioral exists
→ add targeted behavioral anchors

cosmetic
→ standard CI
```

Un structural change non può mai ridurre il numero di test.

Per behavioral field sconosciuto:

```text
Tier 0 + full behavioral anchors
```

Mai zero anchor.

# 18. Historical Anchors

Portare il bootstrap a 15–25 anchor stabili.

```text
5 local bugfix
```

# 20. Anchor token budget reale

`maxTokens` deve essere enforceable durante la run, non solo dichiarato.

Quando:

```text
input + output + relevant reasoning tokens >= maxTokens
```

terminare/classificare:

```text
budget-exceeded-tokens
```

Popolare in `RunCost`:

- inputTokens;
- outputTokens;
- cacheHitTokens;
- toolCalls;
- wallMs;
- modelCostUsd;
- toolCostUsd se disponibile.

# 21. RegressionGate — anchor candidate mancante

Confrontare sull’unione:

```text
baseline IDs ∪ candidate IDs
```

Se baseline ha PASS e candidate non ha record:

```text
REGRESSION
```

oppure `BLOCKED` solo con reason esplicita e policy che lo consente.

Nessun anchor deve poter “sparire” per evitare il gate.

---

# 22. Fix `runGate`

Caricare separatamente:

```text
baselineSummary
candidateSummary
```

Passare:

```text
baselineCurrentSuite = baseline
currentSuite = candidate
```

Non hardcodare:

```text
validityViolations = []
```

Alimentare validity con:

- Session invariants;
- manifest validity;
- fixture validity;
- runtime errors.

# 23. Unified Cost completo

Tipo:

```ts
interface RunCost {
  inputTokens: number;
  outputTokens: number;
  cacheHitTokens: number;
  toolCalls: number;
  modelCostUsd: number;
  toolCostUsd: number;
  wallMs: number;
}
```

North-star:

```text
cost per verified solved task
```

Calcolo:

```text
(modelCostUsd + toolCostUsd) / verifiedSolves
```

Report:

```text
solve rate
cost/verified solve
wall/verified solve
tool calls/verified solve
```

Possibile outcome:

```text
REVIEW_REQUIRED
```

quando solve migliora ma il costo supera una soglia non hard.
