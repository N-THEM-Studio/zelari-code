## Fundamental architecture (first principles)

### 1. `@zelari/core` as a public package

**Current state:** the code is *logically* separated ("Electron-free" comments in AgentHarness, a `src/main/core/` directory that is only lexical) but there is no physical **package boundary**. `src/agents/` (council) and `src/main/core/` (harness + tools) live in the same package as the CLI.

**What is needed:**
- Decide: **monorepo (npm workspaces)** vs **separate repo** (`N-THEM-Studio/zelari-core`)
  - Monorepo: simpler, in sync, but constrains versioning
  - Separate repo: independent versioning, but +1 layer of release management
  - **Recommendation: monorepo** for now - it is a single team, independent versioning can always be done later
- Create `packages/core/` with:
  - `src/main/core/` -> `packages/core/src/harness/`
  - `src/main/core/tools/` -> `packages/core/src/tools/`
  - `src/agents/` (councilApi, roles, promoteMember, skills) -> `packages/core/src/council/`
  - `src/agents/skills/builtin/` -> `packages/core/src/skills/`
  - `src/shared/` (BrainEvent types) -> `packages/core/src/events/`
  - `src/types/` (workspace, context) -> `packages/core/src/types/`
- The `zelari-code` package becomes a thin wrapper: imports `@zelari/core`, handles only CLI/Ink UI

### 2. AgentHarness as single point of truth

Already true. **Validate with an audit:**
- Do all consumers (CLI, council, future GUI) go through `AgentHarness`?
- Are the `electron/` dependencies in comments removed or leftovers?
- Is the public API stable and documented?

### 3. Thin CLI wrapper

Already partially true. Verify:
- `src/cli/app.tsx` (175 LOC post v0.4.2) -> wiring only
- Is all business logic in `@zelari/core`?
- No complex state machine in the UI (it should be in core)?

### Phase 1: Core extraction (1-2 weeks)

**Goal:** `@zelari/core` publishable, separate package.

- [ ] **Monorepo setup**
  - `package.json` -> `"workspaces": ["packages/*"]`
  - Root `package.json` becomes dev/test/tooling only
  - `packages/core/package.json` with `name: "@zelari/core"`, version `0.5.0-alpha.1`
  - pnpm (faster + strict mode) or npm workspaces? -> **npm workspaces** (zero new tools, Andrea already uses npm)
- [ ] **Move files** (see the Architecture section above)
  - Migration script: `git mv` to preserve history
  - Recompute all import paths (`from '../../main/core/...'` -> `from '@zelari/core/...'`)
- [ ] **API surface audit**
  - Export only public functions, hide helpers
  - Add `packages/core/API.md` with examples for every export
  - Full JSDoc on every `export`
- [ ] **CLI refactor**
  - `zelari-code` becomes `import { AgentHarness, runCouncilPure, ... } from '@zelari/core'`
  - `src/cli/` keeps only Ink UI, hooks, slash handlers
  - Verify no residual `from '../main/core/'` or `from '../agents/'`
- [ ] **Build pipeline**
  - `packages/core/tsconfig.json` with `composite: true`, `declaration: true`
  - CLI build depends on core build
  - CLI bundle separate from core bundle (esbuild)
- [ ] **CI updated**
  - `.github/workflows/publish.yml` publishes `@zelari/core` AND `zelari-code` (with dependency)
  - Coupled versioning for now (same tag -> both bump)

**Done when:**
- `npm install` from a clean registry works
- `@zelari/core` importable from an external project via `npm install @zelari/core`
- Integration test: minimal "hello world" CLI using `@zelari/core` directly
- CHANGELOG updated with breaking changes

### Phase 2: Onboarding & DX (1 week)

**Goal:** < 5 minutes to first useful value.

- [ ] **Interactive wizard** on first launch
  - Trigger: `~/.zelari-code/` does not exist OR `ZELARI_FIRST_RUN=1`
  - Steps:
    1. Welcome + small ascii logo (optional)
    2. Provider choice: OpenAI / Grok (OAuth) / GLM / Custom
    3. Connection test with a mini-prompt ("Hello, who are you?")
    4. Preset: "Quick (1 model)" vs "Council (6 members)"
    5. Write `~/.zelari-code/config.json` with the choice
  - Skip wizard: `zelari-code --no-wizard` or `ZELARI_NO_WIZARD=1`
- [ ] **Quick Start presets** in `~/.zelari-code/presets/`
  - `quick.json` (single model, no council, 4 base tools)
  - `council.json` (current default: 6 Dantean roles)
  - `minimal.json` (read-only, no shell)
- [ ] **Improved README**
  - "5 minutes to first value" section at the top (right after install)
  - 3 concrete examples: refactoring, tests, code review (with ASCII output screenshots)
  - Link to the `examples/` directory with demo projects
- [ ] **Concrete examples** in `examples/`
  - `examples/refactor-todo/` (mini project + suggested command)
  - `examples/test-coverage/` (mini project without tests -> with tests)
  - `examples/review-pr/` (mini diff + `/council` invocation)
- [ ] **`/examples` slash command** showing 3 preconfigured quick starts

**Done when:**
- New user (clean `~/.zelari-code/`) -> wizard appears -> 5 minutes -> first useful answer
- README "5 minutes" section tested with 1-2 external people
- 3 examples in `examples/` work end-to-end

### Phase 3: Reliability & truth-seeking (1-2 weeks)

**Goal:** `/council` reliable, visible, verifiable.

- [ ] **Council visible reasoning**
  - Every role shows its own "thinking" (already parsed in `parseThinking`) in a separate panel
  - Right sidebar (or bottom drawer) with a "Roles" tab -> click Caronte/Nettuno/etc -> see the full prompt+output
  - `/council --verbose` toggle for a JSON dump of all events
- [ ] **Headless mode**
  - `zelari-code --headless --task "refactor foo.ts" --output json`
  - No Ink, no TUI -> JSON stream on stdout
  - CI-friendly: exit code 0/1, structured log
  - Use cases: GitHub Action, pre-commit hook, cron
- [ ] **Better grounding**
  - Every council claim must cite at least 1 file:line of the workspace (or be marked "speculative")
  - Automatic validation: if Minosse (critic) cites a non-existent file -> warning
  - The `read_file` tool must be called BEFORE any claim about code
- [ ] **Automatic output validation**
  - If `/council` produces `plan.md`, run `zelari-code --validate-plan .zelari/plan.md` -> checks tasks are atomic, decisions have ADRs, etc.
  - If it produces `risks.md`, check severity + mitigations are present
- [ ] **Better retry + fallback**
  - If a role fails 3x -> swap to another provider (already partially done with `ANATHEMA_FAILOVER`)
  - `/council --no-fallback` for debugging

**Done when:**
- 10 typical council tasks run E2E -> 0 crashes
- Headless mode tested in GitHub Actions
- Visible reasoning tested with a focus group (even just Andrea + me)
- 0% claims about code without a prior `read_file`

## What NOT to do (Low Ego)

- New skills or council roles (resist!)
- Complete TUI rewrite (Ink 6 works, it is tested)
- New LLM providers (3 are enough for v0.5.0)
- Plugin system (defer to v0.6+)
- Web UI (defer to v0.6+, `hermes-workspace` already exists for that)
- MCP server mode (interesting but scope creep)
- Voice mode / TTS (defer, low value)
- Refactors "for cleanliness" without a measurable reason

## Risks & anti-patterns

| Risk | Mitigation |
|---------|------------|
| Monorepo setup breaks CI | Feature branch, CI dry-run on 5 commits, fallback to single repo if blocking |
| Wizard too long -> worsens onboarding | Max 5 steps, skip always possible, sensible defaults |
| Visible reasoning too verbose -> overwhelming | Toggle off by default, opt-in per role |
| `@zelari/core` as a public API blocks future refactors | Strict semver versioning, internal modules in `core/internal/` not exported |
| agy audit finds bugs in Phase 0 that block everything | Normal - that is the point of the audit. Allocate 2-3 buffer days |
| Council reliability regression post headless mode | Mandatory E2E test suite, no merge without 10/10 green |
